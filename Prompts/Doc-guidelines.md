# DragonLib 项目文档约定

本文件约定用 DragonLib 开发的游戏仓库中 `Doc/` 的分类、索引和维护方式，适用于新项目和已有项目。工程目录与创建流程见 [新项目创建提示词](New-project.md)，代码和数据约定见 [面向数据开发约定](DOD-guidelines.md)。

使用方式：让 AI 阅读本文件后再写或整理文档，例如“阅读 DragonLib 的 Prompts/Doc-guidelines.md，按其中约定整理 MyGame 的 Doc 目录”。也可以复制“提示词开始”到“提示词结束”之间的内容放进游戏仓库的 `AGENTS.md`。

## 提示词开始

项目文档放在仓库根目录的 `Doc/`，按“读者要做什么”分类。写新文档前先判断它属于哪一类；一篇文档只讲一个主题，跨类内容拆开并互相链接。

### 1. 目录

```text
Doc/
├─ README.md   文档索引：每篇一行，写用途和状态
├─ Design/     游戏是什么：故事、世界观、美术、玩法设计、调参原则
├─ Plans/      要做什么、做到哪了：路线图、里程碑、进行中的计划
├─ Systems/    当前规则与数据格式：系统行为、资源文件字段、判定规则
├─ Guides/     怎么用：编辑器与工具的操作流程、样例关卡或样例角色的走查
├─ Tech/       怎么改代码：源码分层、扩展入口、技术约束
├─ Records/    带日期的测试、性能或决策记录
└─ Archive/    已被替代或放弃的方案、早期草稿
```

只创建用得到的子目录，不预先放空文件。判断归类时按读者区分：

| 读者想知道 | 放到 |
| --- | --- |
| 这个游戏应该是什么样 | Design |
| 下一步做什么、某项计划完成没有 | Plans |
| 游戏现在按什么规则运行、数据字段是什么意思 | Systems |
| 在编辑器或工具里怎么完成一件事 | Guides |
| 新增代码应该写在哪、遵守什么边界 | Tech |
| 某次验证或决定当时的结论 | Records |
| 以前为什么那样做（已不再适用） | Archive |

同一个系统既有规则又有操作步骤时，规则写进 Systems，操作写进 Guides，两篇互相链接。

### 2. 索引

- `Doc/README.md` 按上面的目录分节，每篇一行：链接、一句话用途、状态。
- 状态只用四种：**现行**（与代码一致）、**进行中**（计划或未完成的实现）、**草稿**（想法，未定）、**已过时**（等待更新或归档）。
- 新增、移动、归档文档时同步更新索引。不在索引里的文档视为不存在。
- 根目录 README 只链接 `Doc/README.md` 和少数主入口，不重复列出全部文档。

### 3. 单篇文档

- 标题之后第一段说明这篇讲什么、给谁看。Plans、Records 和设计定稿写明日期与状态，例如 `> 状态：进行中，2026-10-08`。
- 写真实实现。尚未实现、已知限制和兼容行为单独列出，不把计划写成现状。
- Plans 用勾选项列步骤，每个阶段写验收标准；完成后保留勾选记录，整篇完成或被替代时移入 Archive。
- 文档之间用相对路径链接。移动文件后搜索全仓库的旧路径（包括根 README、`AGENTS.md`、资源目录说明和源码注释）一并修正。
- 文件名用英文 PascalCase，正文语言与项目一致。代码中的类型名、字段名和资源路径用反引号标出，不翻译。
- 源码注释只保留就地需要的信息；设计推导、长流程和教程写进 Doc，并在源码相关位置指向它。

### 4. 维护

- 改动系统行为、数据格式或编辑器流程时，同一次提交中更新对应的 Systems 或 Guides 文档。
- 发现文档与代码不一致：能确定现状就直接改正；不能确定就把状态标为已过时，并在索引写明原因。
- 被替代的文档移到 Archive，开头注明替代者链接，不直接删除。草稿想法确定后并入 Design，未采用的移入 Archive。
- 移动文档用 `git mv` 保留历史；不要在同一次提交里同时大幅移动和改写同一篇文档。
